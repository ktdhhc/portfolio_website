# MemCraft 开发笔记

## 人格分析的设计思考

### 传统做法的问题

常见的人格分析方式是把一大段文本直接交给 LLM，让它在一个 prompt 里完成多维度的人格判断。设计重心放在 prompt 调优上——怎么写 prompt 才能让 LLM 给出更准确的 Big Five 分数、更合理的 MBTI 判定。

这种做法忽略了两个根本问题：

**第一，人格不是通过外部观察可以直接得出的显性结论。** 大部分人格维度隐藏在平时不容易注意到的地方——一个人在压力下的反应、在冲突中的退让方式、在独处时的选择倾向。这些信息散落在文本各处，占比很小，但对人格判断的权重很高。问题在于，LLM 在处理长文本时，对所有信息的注意力分配是相对均匀的。它不会自动给"角色在关键冲突中的微小反应"比"日常对话描写"更高的权重。结果就是，该被注意到的细节被淹没了，不该被放大的表面特征反而被当成了主要依据。

**第二，文本越长，注意力越稀释。** 当涉及 100k 以上的文本时，LLM 的有效注意力会被进一步摊薄。这不只是"分析质量下降"的问题，还意味着成本上升——你用了很多 token 来喂信息，但真正被有效利用的比例很低。

### 我的解法：人格切面 + 综合分析

我没有让 LLM 直接对整篇文本做人格分析，而是把它拆成两步：

**第一步：滑动窗口提取人格切面。** 把文本按窗口切分，每个窗口单独分析，只提取这个窗口能观察到的人格片段——可能是一次冲突中的反应模式，可能是一段关系中的依附倾向，可能是面对选择时的价值排序。每个窗口的分析范围小，LLM 的注意力不会被稀释，反而能更专注地捕捉细节。

**第二步：综合分析。** 把所有窗口的切面汇总，让 LLM 基于这些已经提取好的、有来源标注的切面信息，做最终的人格档案综合。这一步的输入不再是原始长文本，而是结构化的切面列表，信息密度高、噪声低。

这个方法的好处是：

- **更关注细节**：窗口粒度的分析让 LLM 有更多注意力分配给文本中的微妙信号，而不是被大段描写稀释
- **更可追溯**：每个人格判断都能追溯到具体的文本窗口和原始证据，不是 LLM 凭"整体印象"给出的模糊结论
- **更省成本**：不需要把 100k+ 的文本一次性塞进一个 prompt，分窗口处理的总 token 消耗通常更低
- **更能刻画真实人格**：综合多窗口的切面，比单次全局分析更能捕捉到人格在不同情境下的表现差异

## 分步流水线的设计来源

分步设计不是一开始就想到的。最初也试过让 LLM 一步到位生成结构化数据，结果发现：

- 输出质量不稳定，同样的输入跑两次，结果差异很大
- 出了问题无法定位原因——是抽取阶段漏了节点？还是展开阶段搞混了时间线？还是术语替换出了错？
- 无法局部修复，只能整体重跑

后来在 HEART-Bench 的数据复核中观察到：数据质量问题往往是上游偏差的级联放大。一个节点在抽取阶段少了一条 evidence，到展开阶段就可能生成一个缺少支撑的事件，到记忆转换阶段就可能产出一段没有来源的记忆。如果流程本身没有检查和回退机制，问题会一直积累到最终产出才暴露。

这让我确定了分步设计的方向：每一步保存中间结果，上游重跑时下游自动失效，每一步都可以独立审查和重跑。

## Prompt 工程的经验

项目里每个步骤都有独立的 system prompt 和 user prompt 文件，废弃版本也保留在 `deprecated/` 目录。几条经验：

- **格式稳定性比内容质量更重要。** LLM 的分析能力通常够用，但输出格式经常不稳定——有时返回数组，有时返回对象，有时在 JSON 外面包一层 markdown 代码块。prompt 里对输出格式的约束要非常明确，甚至要写"不要输出任何 JSON 以外的内容"。
- **同一个 prompt 在不同模型上表现差异很大。** 在 DeepSeek 上调好的 prompt，换到其他模型可能完全不work。所以 prompt 版本管理很重要，改 prompt 时要记录是针对哪个模型改的。
- **不要让 LLM 做太多事。** 一个 prompt 里塞太多任务（比如同时要求抽取节点、排序、标注问题），结果往往是每个任务都做得很敷衍。拆成独立步骤，每步只做一件事，效果明显更好。

## 踩过的坑

### 节点合并的误合并

滑动窗口抽取会产生重复节点，所以加了规则合并 + LLM 审查。但规则合并有时会把两个不同的事件错误地合并成一个——当它们的 summary 措辞太相似时，merge key 会冲突。后来加了 LLM 审查环节来兜底，但这个问题没有完全根除，只是降低了概率。

### SQLite 并发写入

本地 demo 用 SQLite，LLM 调用是异步的，日志写入经常遇到 "database is locked" 错误。后来在日志写入层加了指数退避重试机制，最多重试 5 次。这个方案在单用户场景下够用，但如果未来要支持多用户，需要换数据库。

### LLM 输出截断

长文本处理时，LLM 的输出有时会被截断（finish_reason=length），但前端和后端都没有处理这种情况，导致解析 JSON 时报错。后来在 LLM 客户端层加了截断检测，并在 prompt 里加了"控制输出长度"的约束。

## 未解决的问题

### 长文本事件时间排序

这是目前最大的未解决问题。LLM 对时间信息的理解是模糊的，尤其当文本里用的是相对时间描述（"那年秋天""几年后""大学毕业后"）时，它很难给出可靠的绝对时间线。

目前的缓解方式：
- 在 preprocess 阶段用正则识别章节/场景边界，提供粗粒度的时间锚点
- 在 review_nodes 阶段让 LLM 对节点做时间排序
- 在 expand_events 阶段用上下文窗口帮助 LLM 理解事件的时间关系

但这些都不够可靠。下一步计划引入 RAG——通过更精细的时间信息检索和上下文关联来辅助排序，而不是完全依赖 LLM 的推理能力。

### 前端耦合度

`App.tsx` 仍然是一个很大的文件，承载了太多编排逻辑。虽然已经拆出了 `AppWorkbenches.tsx`、`AppUI.tsx`、`AppUtils.ts` 和独立页面组件，但核心的状态管理和 API 调用仍然集中在主文件里。这个问题目前优先级不高，但如果要继续扩展功能，需要做更细的拆分。
