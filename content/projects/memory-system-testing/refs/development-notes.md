## 分层诊断方法论

### 设计思路

错题分析的核心挑战是：如何从"结果错了"推导出"哪里出了问题"。我们最终建立了"检索→总结→推理"的三级诊断框架：

1. **检索失败**：检索结果中没有正确答案的原文证据
   - 典型表现：召回了不相关的记忆，或关键证据未被召回
   - 根因：检索算法的召回率问题，或记忆库本身缺失信息

2. **总结失败**：检索到包含答案的信息，但 Agent 没有纳入考量
   - 典型表现：证据在检索结果中，但 Agent 的回答没有引用或使用
   - 根因：LLM 的注意力稀释（上下文过长导致关键信息被忽略）

3. **推理错误**：检索和总结都包含正确信息，但最终仍答错
   - 典型表现：Agent 引用了正确的证据，但推理过程出错
   - 根因：LLM 的推理能力限制，或 prompt 设计问题

这个框架的价值在于：它把模糊的"答错了"变成了可定位的"哪个环节出了问题"，从而可以针对性优化。

### 实践发现

- 检索错误总体占比较高，但不同题型和测试集有差异
- 难度越高的题（如 T5 回忆线索分析、T6 身心互动），推理错误占比越大
- 这说明高阶认知任务的瓶颈不在于"找得到"，而在于"想得明白"

## LLM-as-Judge 的局限性

### 核心观察

用 LLM（GPT5.4）做错题分析时，发现一个根本性问题：**同一份结果并行分析两次，可能得到不同的错误占比**。

这说明 LLM-as-Judge 本身存在"能力天花板"——如果裁判都无法稳定地理解问题，那它的判断就不可靠。

### 设计哲学：human-in-the-loop

这个观察引出了一个工程设计哲学：

- LLM 可以帮助完成很多工作，但也会犯错
- 工作越复杂，错误越隐蔽
- 因此需要人做决策判断、结果验收，引导 LLM 的工作方向
- 只要人还掌握着AI不知道的信息，那么人的介入就有必要

在实践中，我们的工作流程是：LLM 做初步分析 → 人工筛选和验证 → 最终确认错误归因。这个流程既利用了 LLM 的效率，又保证了分析的可靠性。

## 协作经验

### 磨合过程

这是第一次真正和同事协作的项目。一开始的挑战是双方对彼此工作的不了解：

- 我不知道研发同事需要什么检索信息
- 他不知道我的测试集 schema
- 对"错误归因"的理解也有过分歧

### 建立共识

通过持续沟通，我们最终：

- 共同探讨出"检索→总结→推理"的分层诊断方法论
- 明确了各自的职责边界（他负责调用记忆系统和捞回结果，我负责处理和分析）
- 建立了高效的工作流程

### 实际产出

分析结果直接优化了记忆系统：

- 优化了记忆系统的 prompt
- 优化了记忆总结的触发频率和流程

## KnowMe-Bench 评测体系观察

### 数据集质量发现

在测试过程中，发现了评测体系本身的一些问题：

1. **评分问题**：judge 评分时不会参考 evidence，只能看到 correct answer，导致误判
2. **数据集问题**：dataset1 缺少 300+ 条记忆，32 道题的 evidence 指向缺失记忆
3. **数据处理问题**：时间戳解析 bug（summary 出现大量 2026 时间点）；检索 bug（有 evidence 但无 summary）

### 独立思考

"如果裁判自己都无法理解人，怎么判断考生是否真正理解"——这个观点不仅是对 KnowMe-Bench 评测体系的批评，更是对整个 LLM-as-Judge 范式的反思。

在高阶认知任务（如心理分析、动机推断）上，LLM 的判断能力本身就有限，用它来评判另一个 LLM 的表现，存在根本性的能力天花板。
