# Aindexer 开发笔记

## 技术架构

### 整体架构

Aindexer 采用本地化应用架构，前端基于 React，后端基于 FastAPI，数据存储使用 SQLite + 本地文件系统。

| 层次 | 技术 |
|---|---|
| 后端 | FastAPI、Pydantic、SQLite、本地文件存储 |
| 前端 | React 18、TypeScript、Vite、TanStack Router、TanStack Query、Zustand |
| 桌面端 | Tauri 2、Rust |
| 文档解析 | PyMuPDF、pdfplumber、python-docx |
| 检索与能力支撑 | SQLite FTS5、流式问答、流式翻译、取消控制、工作区隔离、备份恢复 |

### 核心模块

| 模块 | 作用 |
|---|---|
| Workbench | 上传、浏览、搜索、排序、索引修订和导出 |
| Chat | 围绕文献提问，支持三种模式 |
| Translator | PDF 选区翻译、原文对照、历史回看 |
| Config | Provider、模型默认值、字段模板、工作区管理 |

### 对话功能：三层数据分层 + LLM 按需读取

对话功能的核心设计是三层数据分层：

| 层级 | 内容 | 作用 |
|---|---|---|
| 元数据 | 标题、作者、年份、期刊、摘要、关键词 | 对话开头默认注入，让 LLM 初筛定位相关文献 |
| 索引数据 | 结构化信息（核心观点、重要 claims） | LLM 按需读取，确定准确信息 |
| 原文件 | 文献原文 | 检索到后读取，找到原文出处 |

**按需读取机制**：

1. 元数据在对话开头默认注入
2. LLM 从标题、关键词等元数据初筛定位相关文献
3. 定位到对应的索引确定准确信息
4. 如果检索不到，再读取其他相关性更低的索引
5. 检索到后读原文找到原文出处
6. 每一步都需要思考已有信息是否足够回答用户问题，如果是就直接回答，否则进入下一轮读取推理

**三种模式**：
- 全景模式：只读元数据和索引
- 精读模式：只读特定文献
- 默认模式：三层按需读取

这个设计大大降低了 token 使用，在海量文献中检索模糊信息的场景中非常好用。

### 翻译功能：手写 PDF 查看器 + 透明蒙版对齐

翻译功能的难点在于划词翻译需要鼠标选中 PDF 中的内容并提取出来才能翻译，而当时没有现成的依赖可以用。

**解决方案**：手写了一个简易的 PDF 查看器，载入文件时自动提取文字，并做成透明蒙版对齐原文位置。这个功能打磨了很久才找到可以准确对齐的技术策略。

## 版本迭代

### V1 — 基础文献管理

- 文献上传与元数据提取
- 基础搜索功能
- SQLite 存储

### V2 — 结构化索引与翻译

- 字段模板机制

### V3 — 体验优化与发布

- 搜索预览优化
- 导入导出备份
- 发布至 GitHub 和产品主页
- AI Coding 工具深度集成辅助开发

- 前端从 legacy 静态前端演进到 V3.5 Editorial Lab
- 引入 `v35.css` 设计语言，统一前端样式

### V4 — 桌面端落地

- 引入 Tauri 2 桌面壳层
- 桌面端会话化改造
- 开发重心转向桌面端，Web 版仅保留基础兼容

## 技术债与可维护性

### 产生原因

1. 前期没有做好规划
2. 交互设计变动比较大，样式飘忽不定
3. 改动位置也很零散
4. 最终导致几个文件体积膨胀严重，改起来也十分艰难

### 可维护性热点

- `backend/app/routers/index.py`：同时承担路由、任务编排、进度逻辑和失败回退
- `backend/app/repository.py`：较大，混合多个领域的持久化逻辑
- `frontend-v3/src/app/chatStore.ts` 与 `workbenchChatStore.ts`：承担较多会话与流式状态协调
- `frontend-v3/src/shared/styles/v35.css` 与 `styles.css` 并存，样式隔离是前端主要风险点之一

### 解决办法

针对性地把那几个大文件按照功能拆分出来避免继续膨胀。

## 开发方法论

### 从"抽奖式编程"到规范开发

Aindexer 是第一个 vibe coding 项目，当时没有开发经验，以当时的能力无法做出更好的技术选型。在开发过程中，从"抽奖式编程"逐步过渡到定规则、写文档、做决策和手动验收等习惯。

**一个具体的教训**：一个看起来很普通的交互 bug 修了很久都没有进展，最后深入调查才发现四五个问题耦合在一起，没办法直接测出来具体是哪里的问题，只好全部删掉重新写。这个教训让我意识到了模块拆分的重要性。

### 文档体系的建立

经过试错、增加、删减或压缩，最终沉淀出适合自己的文档体系：

- **AGENTS.md**：不变事实和开发规范
- **CURRENT_STATE.md**：当前项目的准确事实，需要及时更新
- **FRONTEND_DESIGN.md**：前端交互设计规范，避免设计漂移
- **plans/**：曾经或新的开发规划，便于以后回看

最后也总结成属于自己的一个 skill，可以根据一份产品大纲或者已有 demo 快速构建出上述的文件体系。

### 开发重心的反思

前期浪费了很大时间在 API key 和 UI 优化上面，主要还是因为没有抓住开发重心。

**正确的开发重心**：应该留在"文件上传→生成检索→队列设计→入库和修订"这一条路径上持续打磨，因为这是产品的核心，这个功能没做好会留下很多技术债。其次的重点应该放在 Agent 对话中。

## 踩过的坑

### 样式隔离问题

`frontend-v3/src/styles.css` 与 `frontend-v3/src/shared/styles/v35.css` 并存，改样式时必须防止历史规则污染 V3.5。这是前端主要风险点之一。

### 索引任务的状态管理

索引过程的状态包括 `status` 和 `stage` 两个维度，失败时会写入 fallback 模板，并把状态置为 `needs_review`，而不是简单失败后无内容。这个设计避免了用户在索引失败后丢失数据。

### Chat 来源编号的稳定性

Chat 来源编号现在由后端基于当前上下文和 `seq_num` 统一生成，前端不再发送或持久化 `source_map`。这个改动避免了来源编号的不一致性问题。
