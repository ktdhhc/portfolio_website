# 个人主页简历容器产品大纲

## 一、产品定位

本项目是一个面向求职场景的个人主页，核心目标不是展示技术炫技，而是作为一份 **稳定、可访问、可维护、可交互的在线简历容器**。

它承担三个作用：

1. **简历展示入口**
   让面试官、HR、招聘负责人能够快速了解候选人的基本背景、经历、项目、能力方向和联系方式。

2. **项目说明入口**
   通过结构化项目页面展示候选人的代表项目，说明项目背景、个人职责、关键设计、产出结果和可验证材料。

3. **Candidate Agent 辅助入口**
   内嵌一个基于候选人资料构建的问答 Agent，帮助访客快速理解候选人的经历、项目细节、岗位匹配度、优势与不足。

本产品的本质不是“AI 分身产品”，而是 **可对话的简历辅助系统**。Agent 是增强层，不是主体。即使 Agent 不可用，主页本身也必须能够完整承担简历展示功能。

---

## 二、核心设计原则

### 1. 稳定优先

简历页面必须优先保证稳定访问。
公开页面应尽量静态化，避免因为后端、模型 API、数据库或 Agent 服务异常导致简历主体不可访问。

### 2. 低维护优先

内容更新应尽量通过 Markdown / JSON / 配置文件完成，避免一开始建设复杂后台。
项目资料、个人介绍、FAQ、Agent 知识内容应尽量放在同一个代码仓库中，便于版本管理和回滚。

### 3. Agent 辅助而非替代本人

Candidate Agent 只能基于已提供资料回答问题，不应编造经历、夸大成果或替候选人做现实承诺。
Agent 的价值在于帮助访客快速理解资料，而不是制造一个完全拟人的虚拟候选人。

### 4. 数据采集克制透明

可以收集访问、点击、下载、Agent 提问等行为数据，用于优化简历表达和了解访客关注点。
但应避免过度追踪，不主动识别访客身份，不保存完整 IP，不收集不必要的个人信息。
Agent 输入框附近应提示：提问内容可能会被记录用于改进页面体验，请勿输入敏感或机密信息。

### 5. 失败可降级

Agent 调用失败时，页面应提示访客查看静态简历和项目页。
数据统计失败时，不应影响页面正常浏览。
后台不可用时，不应影响公开页面。

---

## 三、目标用户

### 主要用户

1. **HR / 招聘人员**
   需要快速判断候选人是否符合岗位要求。

2. **面试官 / 团队负责人**
   需要了解候选人的项目经验、能力边界、思考方式和可追问点。

3. **合作方 / 推荐人**
   需要快速了解候选人的方向、作品和联系方式。

### 管理用户

1. **候选人本人**
   需要维护简历内容、查看访问数据、分析访客问题、优化页面表达。

---

## 四、核心功能范围

## 4.1 公开页面

### 首页

用于快速传达候选人是谁、适合什么方向、有哪些核心能力。

内容包括：

* 姓名 / 标识
* 一句话定位
* 能力标签
* 核心方向
* 项目入口
* 简历下载入口
* Candidate Agent 入口
* GitHub / 邮箱 / LinkedIn 等联系方式

### 在线简历页

用于承载完整简历内容。

内容包括：

* 教育经历
* 工作 / 实习 / 项目经历
* 技能栈
* 研究或产品方向
* 代表项目
* 可下载 PDF 简历

该页面必须在没有 Agent 的情况下也能独立成立。

### 项目列表页

用于展示代表项目卡片。

每个项目卡片包括：

* 项目名称
* 一句话说明
* 项目类型
* 个人角色
* 核心能力标签
* 项目详情入口
* GitHub / Demo / 文档链接，若有

### 项目详情页

用于详细说明项目价值。

每个项目详情页建议采用统一结构：

* 项目背景
* 解决的问题
* 我的职责
* 核心设计
* 技术或工具
* 产出结果
* 难点与复盘
* 可验证材料
* 可追问问题

### Candidate Agent 页面

用于和候选人资料对话。

支持的基础能力：

1. 快速介绍候选人
2. 解释候选人项目
3. 分析岗位匹配度
4. 总结优势与不足
5. 生成建议面试问题
6. 回答基于简历和项目资料的具体问题

Agent 不应承担：

* 替候选人承诺薪资
* 替候选人安排面试
* 替候选人表达最终求职意向
* 回答私人敏感信息
* 编造不存在的经历或成果
* 代替真实面试沟通

## 五、Agent 产品边界

## 5.1 Agent 的定位

Candidate Agent 是一个 **资料问答助手**，不是完全人格化的数字分身。

推荐命名：

* Candidate Agent
* Ask Kaho Agent
* 和我的简历对话
* Resume Agent

推荐说明：

> 这个 Agent 基于我的简历、项目文档和公开作品资料构建，用于帮助你快速了解我的经历、项目细节、能力方向和岗位匹配度。它不会替我承诺现实事项，无法确认的信息会明确说明。

## 5.2 Agent 的回答原则

Agent 应遵守以下规则：

1. 只根据候选人提供的资料回答。
2. 资料不足时明确说明无法确认。
3. 不编造职位、成果、数据、合作方或项目影响力。
4. 面对岗位匹配问题时，同时说明匹配点、风险点和建议追问。
5. 面对质疑时，不回避短板。
6. 不披露私人信息。
7. 不替候选人做现实承诺。
8. 语气专业、克制、清晰。

## 5.3 Agent 的推荐功能

第一版只保留高价值功能：

* 自我介绍
* 项目问答
* 岗位匹配分析
* 优势与不足总结
* 面试问题生成
* JD 粘贴分析

暂不做：

* 长期记忆（跨天以上的会话历史持久化）
* 面试官画像
* 多用户系统
* 多 Agent 协作
* 自动学习访客偏好
* 复杂后台训练系统
* 自主更新简历内容

第一版保留短期记忆：同一访客（基于浏览器 localStorage 标识）在一天内重开页面后仍可延续之前的对话上下文，隔天自动清空。

## 六、数据采集范围

## 6.1 可以采集的数据

用于优化页面和简历表达：

* 页面访问时间
* 访问页面路径
* 简历下载次数
* 项目点击情况
* GitHub / 邮箱 / 外部链接点击
* Agent 打开次数
* Agent 提问内容
* Agent 回答状态
* 模型调用耗时
* Agent 无法回答的问题类型

## 6.2 不建议采集的数据

为了避免过度追踪，默认不采集或不保存：

* 完整 IP 地址
* 访客真实姓名
* 访客邮箱
* 访客公司身份
* 设备指纹（指 Canvas/WebGL 等硬件特征指纹，不含 localStorage 客户端标识）
* 精确地理位置
* 跨站追踪数据
* 与求职无关的私人信息

## 6.3 Agent 提问内容处理

Agent 提问内容可能包含敏感信息，因此应采取克制策略：

* 页面提示访客不要输入敏感或机密信息
* 提问记录仅用于改进简历和 Agent 表达
* 提问原文入库永久保存，不做自动脱敏；由页面提示明确责任边界
* 管理者可在 admin 面板不定时导出和手动清理提问记录
* 不公开展示访客提问内容
* 不将完整提问内容发送到第三方分析平台

## 七、后台形态

本项目不需要一开始建设复杂后台。
后台可以分为三个层级：

## 7.1 第一阶段：无后台页面

只使用：

* 基础访问统计
* Agent 调用日志
* 数据库记录
* 手动查看或导出数据

适合项目初期，开发成本最低。

## 7.2 第二阶段：极简私有面板

增加一个受保护的 `/admin` 页面，只供候选人本人访问。

面板展示：

* 今日 / 本周访问量
* 热门页面
* 简历下载次数
* 项目点击排行
* Agent 高频问题
* Agent 失败记录
* JD 分析次数
* 访客最关注的项目

该后台用于查看数据，并提供提问记录的导出与手动清理能力（按时间范围删除、单条删除、全清），不做其他管理系统。

## 7.3 第三阶段：内容运营面板

当后续维护需求增加时，再考虑增加：

* 项目内容编辑
* FAQ 管理
* Agent 知识库管理
* 高频问题转 FAQ
* 不同岗位版本的简历配置
* 不同投递渠道的数据对比

第一版不建设该能力。

## 八、权限边界

公开页面允许所有访客访问：

* `/`
* `/resume`
* `/projects`
* `/projects/[project]`
* `/agent`

公开接口允许访客调用，但只能写入数据：

* `POST /api/track`
* `POST /api/chat`

私有页面和私有接口只允许候选人访问：

* `/admin`
* `GET /api/admin/logs`
* `GET /api/admin/stats`

权限原则：

> 访客可以浏览页面、使用 Agent、上报行为事件，但不能查看任何后台数据。

## 九、推荐技术形态

## 9.1 第一版推荐

以低维护为优先，推荐：

* 前端托管：Cloudflare Pages
* API：Cloudflare Workers / Pages Functions
* 模型调用：外部 LLM API
* 模型网关：AI Gateway，可选
* 数据记录：D1 / Analytics Engine
* 内容管理：Markdown / JSON
* 后台权限：Cloudflare Access，或简单管理员 token
* RAG：暂不上

## 9.2 内容组织方式

建议将个人资料放入代码仓库：

```text
content/
  profile.md
  resume.json
  faq.md
  projects/
    aindexer.md
    agent-memory.md
  agent/
    system-prompt.md
    answer-rules.md
```

这样可以通过 Git 管理版本，避免数据库后台带来的维护成本。

## 9.3 后续升级方向

当内容量增加或查询复杂度上升后，再考虑：

* Cloudflare Vectorize
* Supabase pgvector
* 专业向量数据库
* 项目内容管理后台
* 多版本简历系统
* 更完整的数据分析面板

## 十、MVP 范围

第一版 MVP 应包含：

1. 首页
2. 在线简历页
3. 项目列表页
4. 2–4 个项目详情页
5. PDF 简历下载
6. Candidate Agent 页面
7. 预设问题按钮
8. JD 粘贴分析
9. 基础访问统计
10. 点击事件记录
11. Agent 提问记录
12. 简单隐私提示
13. Agent 失败降级提示

第一版不包含：

* 用户登录系统
* 复杂后台
* 多用户 SaaS
* 自部署大模型
* 长期记忆系统
* 多 Agent 协作
* 复杂 RAG 管理
* 自动爬取和更新简历资料

---

## 十一、产品边界总结

本项目不是：

* AI 聊天机器人展示项目
* 完整数字分身产品
* 多用户求职平台
* 复杂数据分析系统
* 自部署模型工程项目
* 招聘自动化系统

本项目是：

* 一份稳定的在线简历
* 一个结构化个人作品集
* 一个可对话的候选人资料助手
* 一个轻量的访客行为反馈系统
* 一个便于长期维护和迭代的求职入口

最终目标是：

> 让面试官更快理解候选人，让候选人更清楚访客关注什么，同时保持系统稳定、克制、低维护。
